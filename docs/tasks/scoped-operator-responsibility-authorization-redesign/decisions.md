# Task Decisions: scoped-operator-responsibility-authorization-redesign

Record temporary or local choices that help reviewers understand implementation. Durable choices
must move to an ADR that supersedes ADR-0013 before implementation cutover.

| Date | Decision | Context | Alternatives | Consequences | ADR required |
| --- | --- | --- | --- | --- | --- |
| 2026-07-30 | Treat all current users, roles and persisted application data as disposable demo data; do not backfill legacy roles | Owner explicitly stated old users/roles are irrelevant and all DB data may be deleted for the ideal architecture | Preserve/backfill roles; dual long-term compatibility | Enables clean model and destructive local reset; no production/in-place migration | Yes |
| 2026-07-30 | Make organization membership roleless and non-authoritative beyond safe organization-shell access | Role-at-add and later responsibility assignment duplicate authority concepts | Keep one broad membership role; custom ABAC engine | Every privilege becomes an explicit scoped responsibility | Yes |
| 2026-07-30 | Use a closed responsibility vocabulary with typed per-scope persistence and one central capability evaluator | Need exact FKs, tenant lineage and reviewable bundles | Generic FK grant table; arbitrary per-user capability rows | More tables/code, stronger integrity and simpler authorization review | Yes |
| 2026-07-30 | Require exact scenario-approver assignment; no organization/project approver inheritance initially | Organization-wide approver is too broad | Organization role; project inheritance; policy-selected roles | Strong least privilege; requires explicit assignment and readiness handling | Yes |
| 2026-07-30 | Organization/global administrators do not implicitly receive protected content or tool approval | Administration and sensitive data/side-effect approval are separate duties | Admin has all tenant authority | Requires additional assignments but prevents privilege concentration | Yes |
| 2026-07-30 | Global- and organization-administrator assignments cannot expire | Time-based expiry could remove the last effective administrator without an atomic replacement | Permit expiry with periodic readiness checks | Prevents expiry-driven lockout; temporary admin elevation remains out of scope | Yes |
| 2026-07-30 | Project administrators may delegate scenario viewer/editor only; organization administrators grant scenario approval/release/runtime responsibilities | High-risk child delegation would let project admins manufacture stronger authority | Permit all child responsibilities; forbid all project-admin delegation | Preserves useful authoring delegation without approval/release/runtime escalation | Yes |
| 2026-07-30 | Scenario-to-document-set retrieval remains a two-sided authorization | Scenario authority and protected-content custody must remain separate | Let either scenario or document manager bind and grant alone | Requires coordinated request/approval but prevents one actor from manufacturing both sides | Yes |
| 2026-07-30 | Treat consumer and human initiator as different typed identities; apply self-approval denial only to a verified human initiator | Current code compares `Consumer.subject` with human username | Keep string comparison; remove all separation of duties | Removes false equality and makes human self-approval meaningful | Yes |
| 2026-07-30 | Remove project owner membership as authority/product ownership; project responsibilities represent ownership | Existing owner membership overlaps project administrator assignment | Keep informational/auth owner field | Simplifies authority; GitOps/forms/fixtures must change | Yes |

| 2026-07-30 | Begin implementation of the approved responsibility-based authorization design; defer the destructive reset until clean-install evidence and exact-target review | Owner explicitly requested implementation after approving the plan | Keep task planned; reset immediately | Authorizes code/schema/auth changes now without deleting data prematurely | No |
